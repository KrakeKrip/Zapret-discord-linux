# TASK-002 — Общая логика управления для GUI и Textual

Статус: готов к передаче GLM. TASK-001 принят commit `624f799`; дерево после приёмки было чистым. Этот TASK и план будут отдельным подготовительным commit Codex. Перед началом использовать фактический HEAD и git status.

## Контекст

Рабочая папка: `/home/atlkhnv/Zapret-discord-linux`.

Пользователь утвердил графическое приложение и запуск терминального интерфейса Textual. Оба могут быть открыты одновременно. Общие требования: одна блокировка системных изменений, перечитывание фактического состояния, отказ от сохранения устаревших данных, отсутствие остановки сервиса при закрытии интерфейса.

План интерфейсов: GUI на PySide6 (Qt Quick / QML), TUI на Textual. Эти зависимости НЕ добавляются в данном TASK. Точные версии и установка будут определены в задачах интерфейсов и упаковки.

Сегодня app.py совмещает UI, CLI и управление. Прежде чем создавать новые экраны, нужно выделить независимую от интерфейса логику, сохранив поведение.

Изучи ARCHITECTURE.md, принятую реализацию app.py, diagnostics.py, tests/test_core.py и tests/test_profiles.py. Установщик и setup.py читать по необходимости для проверки импортов и интеграции. Не читать весь проект без необходимости.

## Цель

Создать общий модуль управления, который можно использовать из GUI, Textual и существующего CLI без импорта whiptail-экранов и без побочных действий при импорте.

## Что сделать

1. Создать `src/zapret_console/core.py`. Перенести туда логику подключения к адаптеру, валидации и чтения конфигурации, атомарных записей, профилей и системных операций. Для зависимостей и путей использовать явный контекст Controller/BackendContext вместо дублированных глобальных ROOT/STATE/KNOWN/UNIT в разных модулях. Детали внутренних вспомогательных функций выбрать по существующему стилю.
2. Оставить в app.py CLI-разбор, whiptail и взаимодействие с пользователем. UI делегирует общему модулю; не содержит второй реализации операций записи и восстановления.
3. В core не использовать input(), whiptail, clear, вывод сообщений на экран или выход из процесса. Возвращать данные и возбуждать ошибки; сообщения и коды выхода формирует CLI/UI. Вызовы systemctl допустимы как часть запрошенных операций, но не при импорте или создании контекста.
4. Проверки доверенности, получение существующей блокировки STATE/.lock и dispatch административных изменений сделать общей точкой входа в core. CLI вызывает её после проверки прав; будущие интерфейсы будут обращаться через привилегированный launcher. Проверка root также должна находиться в общей точке входа, а не только в UI. Сохранить существующее исключение для read-only runtime.
5. Общая блокировка должна покрывать все существующие изменения конфигурации, профилей и управления сервисом; проверка, операция, перезапуск и возможное восстановление выполняются под ней. Сохранить неблокирующий отказ при занятой блокировке, без второго lock-файла для каждого интерфейса.
6. Адаптировать существующие тесты к модулю без снижения проверяемого поведения. Добавить проверку двух независимых процессов, использующих общий lock в временном каталоге: пока один удерживает блокировку, другой не выполняет мутацию; после освобождения может выполнить её. Достаточно стандартной библиотеки и подмены системных действий.

## Scope

Входит: выделение общего слоя, делегирование из старого CLI/меню, сохранение контрактов и тестирование общей блокировки.

Не входит: графические окна, Textual, новые зависимости, новая установка, фоновой демон, D-Bus/HTTP-сервер, новые возможности профилей, исправление несвязанных ошибок. Протокол GUI-аутентификации и защита от устаревших данных будут отдельным TASK-003 до запуска двух новых интерфейсов.

PRODUCT.md, ARCHITECTURE.md, TASKS.md, DECISIONS.md и файл TASK ведёт Codex. GLM не редактирует их без отдельного указания. Для нового модуля добавить короткие docstrings контрактов.

## Ограничения

- Сохранить Python 3.10+ и существующие публичные команды, аргументы, JSON-статус и форматы файлов.
- Сохранить known-good.json, previous.json и именованные профили принятого TASK-001.
- Сохранить восстановление конфигурации при неудачном перезапуске и отсутствие запуска остановленного сервиса при смене настроек.
- Подмены в тестах не должны скрывать исчезновение проверок доверенности или права администратора.
- Не менять реальную установку, сервис и firewall. Все изменения и проверки — в исходниках, временных каталогах, с mocks.
- Если перемещение ломает импорт setup/diagnostics, допустима только необходимая адаптация этих импортов. Объяснить сопутствующие изменения в отчёте.

## Ожидаемое поведение

Существующий пользователь запускает CLI/whiptail и получает прежние возможности. Разработчик получает общий слой с данными и операциями, независимый от библиотек интерфейса. Два процесса не изменяют сервис или файлы одновременно через общий административный путь.

## Критерии приёмки

1. Импорт core и создание контекста не вызывают systemctl, sudo, записи, диалоги или вывод.
2. Конфигурация, профили и системные операции имеют единственную реализацию в общем слое.
3. Существующие CLI и JSON-контракты сохранены; регрессионные тесты предыдущих TASK проходят с сохранёнными утверждениями поведения.
4. Права администратора и доверенность проверяются в общем административном пути, независимо от UI.
5. Тест двух процессов подтверждает отказ конкурирующей мутации и успешное продолжение после освобождения lock.
6. Профили, отмена изменений и восстановление после ошибки работают через общий слой.
7. GUI/Textual не импортируются и не устанавливаются в данном TASK.

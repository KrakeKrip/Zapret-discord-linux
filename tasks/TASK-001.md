# TASK-001 — Именованные профили подключения

## Контекст

Рабочая папка: `/home/atlkhnv/Zapret-discord-linux`.

Сейчас приложение сохраняет только один рабочий профиль в `known-good.json` и предыдущую конфигурацию в `previous.json`. Нужна возможность хранить несколько настроек для разных подключений и выбирать их через меню.

Изучи `ARCHITECTURE.md`, `src/zapret_console/app.py` (config, validate, atomic_write, apply_config, admin, main), `tests/test_core.py`. При необходимости изучи установщик, чтобы проверить совместимость; менять установщик не требуется.

Перед началом проверь git status, git diff и git diff --cached, зафиксируй HEAD. До подготовки этого задания дерево было чистым, HEAD — `015ec39`; документ TASK будет отдельным подготовительным commit Codex. Используй фактический HEAD на момент старта.

## Цель

Пользователь сохраняет несколько именованных конфигураций, видит их список, восстанавливает выбранную и удаляет ненужную. Существующий рабочий профиль и отмена последнего изменения продолжают работать.

## Что сделать

1. Добавить хранение в `STATE / 'profiles'`: один файл `<name>.json` на профиль. Формат содержимого — тот же объект пяти полей конфигурации, который возвращает config(); без дополнительных метаданных.
2. Добавить операции списка, сохранения, явной замены, восстановления и удаления. Каталог вычислять от актуального STATE, чтобы временные каталоги тестов работали корректно.
3. Добавить раздел «Именованные профили» в существующее меню сохранённого профиля. В нём доступны список с названием, стратегией и интерфейсом, сохранение текущей настройки, восстановление и удаление выбранной.
4. Имя профиля: 1–48 ASCII-символов, первый — латинская буква или цифра, остальные — латинские буквы, цифры, `_` и `-`. В поле ввода объяснить ограничение. Пустой ввод, пробелы, точки, разделители пути и shell-текст отклоняются до изменений файлов.
5. Если имя уже занято, обычное сохранение отказывает без перезаписи. Меню предлагает отдельное подтверждение замены; административная операция замены должна быть явно отличима от обычного сохранения. Удаление из меню также требует подтверждения.
6. Восстановление выполнять через существующий apply_config и validate. Все изменения профилей — через установленный привилегированный launcher и существующую блокировку. Чтение списка не требует sudo.
7. Добавить релевантные unittest и кратко описать пользовательский сценарий в README.md.

## Scope

Входит: локальные именованные профили, меню, административные операции, тесты и описание использования.

Не входит: автоподбор стратегии, автоматическое переключение по сети, импорт/экспорт, обновление адаптера, смена версии, изменение мастера установки или диагностики. Не переписывать app.py целиком. При необходимости допустим небольшой модуль для хранения профилей.

Не менять PRODUCT.md, ARCHITECTURE.md, TASKS.md, DECISIONS.md и этот TASK: их актуализирует Codex после review.

## Ограничения

- Не добавлять зависимости.
- Сохранить существующие CLI-команды и JSON-статус.
- Не переносить и не изменять known-good.json и previous.json ради новой функции. Отсутствие каталога profiles нормально для старой установки.
- Новые административные операции должны повторно проверять имя и входные данные независимо от UI.
- Не допускать выхода за каталог profiles. Символические ссылки вместо каталога profiles или файла профиля отклонять. Перед привилегированным чтением, заменой или удалением существующих объектов проверять доверенность путей существующим механизмом trusted().
- Запись профиля атомарная. Сохранение и удаление не меняют conf.env и не вызывают systemctl.
- Не изменять установленную копию, реальный сервис и firewall при разработке и самопроверке. Использовать исходники, временные каталоги и mocks.

## Ожидаемое поведение

Пользователь сохраняет `home` со стратегией alt11, меняет настройки и сохраняет `mobile` со стратегией alt10. Оба профиля остаются доступны. При восстановлении `home` применяются все пять сохранённых полей, а не только стратегия.

Активный сервис перезапускается через существующий механизм восстановления при ошибке. Остановленный сервис остаётся остановленным. Отмена удаления или замены ничего не меняет.

Пустой список показывает понятное сообщение. Повреждённый профиль не ломает весь список: показывается как недоступный для восстановления либо пропускается с явным сообщением. Его содержимое не выполняется. Ошибка чтения или восстановления объясняется пользователю; конфигурация не изменяется при невалидном профиле.

## Критерии приёмки

1. Можно сохранить два разных профиля, получить детерминированный список и восстановить каждый со всеми пятью полями.
2. Сохранение под занятым именем не меняет файл; явная замена работает после подтверждения в меню.
3. Удаление затрагивает только выбранный профиль; отмена подтверждения не меняет файлов.
4. Недопустимые имена, ссылки, отсутствующие и повреждённые файлы не приводят к записи вне profiles или изменению conf.env.
5. Восстановление с отсутствующей стратегией или интерфейсом отклоняется до изменения конфигурации.
6. Для остановленного сервиса восстановление не вызывает запуск; для активного используется существующий перезапуск и возврат конфигурации при ошибке.
7. Старые save-good, restore-good и restore-previous сохраняют прежнее поведение. Повторная установка и удаление интерфейса не получают логики очистки профилей.
8. Тесты проверяют операции хранения, перечисленные ошибки, отмену UI-подтверждений и интеграцию восстановления с apply_config. Проверка доверенности не должна полностью исчезнуть под mocks в тестах новых защит: отдельно проверить отказ для символических ссылок.

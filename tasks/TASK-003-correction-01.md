## 1. Строгая проверка ответов helper

Файл: client.py, _parse_response / _run.

Сейчас проверяется только тип строки code, но не допустимость кода и его согласованность с ok; exit code игнорируется при любом структурно распознанном JSON. Воспроизведено Codex:

- `{protocol:1, ok:true, code:'conflict', message:'', data:null}`, exit 0 принимается как успешный ответ.
- ok:true с code:'future_unknown' принимается.
- ok:true/code:'ok', exit 1 принимается как успех.

Это нарушает контракт и может показать успех при неуспешной/несовместимой операции.

Исправить:
- Допустимые коды helper v1: ok, busy, conflict, invalid_request, permission_denied, operation_failed. auth_* и transport_error формирует только клиент, не helper.
- Только ok:true/code:ok/exit:0 — успешный ответ. Ошибки helper: ok:false, один из пяти error-кодов, exit:1. Противоречия или неизвестный код => transport_error; повтор операции не выполнять.
- Для неясного результата сообщать, что необходимо перечитать состояние; не утверждать отмену операции.
- Отмена/отказ pkexec 126/127 без ответа распознаётся только если действительно использовался pkexec. Сейчас capture_stderr=True также для root-ветки; root launcher с 126/127 без ответа должен давать transport_error, не отмену авторизации. Передавать признак транспорта явно.
- Корректные busy/conflict/error-ответы остаются различимыми, а pkexec-отмена и отсутствие авторизации сохраняют нынешнее поведение.

Добавить транспортные тесты для всех перечисленных противоречий, валидных error-ответов exit 1 и root-ветки с 126/127 без JSON. Проверять один вызов subprocess, без повторов.

## 2. Неполный snapshot получает revision без явной ошибки

Файл: core.py, snapshot / _read_file_state / _admin_locked.

Ошибки чтения known-good.json и previous.json хешируются маркером error, но не отражаются в данных snapshot. Codex подменил чтение known-good.json на PermissionError (через существующий status error): snapshot вернул config_error=None, profiles_error=None и обычную строковую revision. Пользователь не видит неполноты; при другом доступе root-helper результат превращается в повторяющийся conflict после каждого обновления.

Исправить контракт:
- Добавить `revision_error` с понятным сообщением о файлах/каталоге, которые не удалось прочитать, либо null при полном чтении. Если read error не позволяет получить все исходные байты для сравнения — revision=None. Не считать маркер ошибки полноценной ревизией данных.
- Тот же отказ готовности для отсутствующего/невалидного conf.env и запрещённых объектов profiles (ссылка вместо каталога/именованного файла, объект вместо каталога). Существующие config_error/profiles_error/ошибки отдельных профилей сохранить. Обычная повреждённая JSON-конфигурация именованного профиля, байты которой прочитаны, по-прежнему допускает revision: профиль можно удалить или заменить.
- Отсутствующие legacy-файлы и profiles — нормальный полный snapshot, не read error.
- При повторной проверке под lock непригодный snapshot даёт явную operation_failed через endpoint до любых записей и restart. Не разрешать мутацию на основании одинакового маркера error и не сводить проблему чтения к обычному conflict.
- При ошибке перечисления profiles вернуть явный непригодный snapshot, не терять причину исключения. Не менять настоящие файлы и не добавлять запрос root для чтения.

Тесты: ошибка чтения каждого legacy-файла, ошибка чтения именованного файла/перечисления каталога, невалидный config, запрещённые ссылки; revision=None и понятная ошибка, отказ мутации без записи/restart. Отдельно сохранить тест повреждённого JSON: доступные байты дают revision и изменение байтов меняет её. Тесты отсутствующих файлов и каталога должны продолжать проходить.

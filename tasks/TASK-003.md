# TASK-003 — Общий клиент операций и защита от устаревших данных

## Контекст

Рабочая папка: `/home/atlkhnv/Zapret-discord-linux`. TASK-002 принят commit `8720081`: core содержит BackendContext и единый admin_command с root-проверкой и STATE/.lock. Существующий whiptail вызывает установленный launcher через sudo, но результат рассчитан на человека. Будущим GUI и Textual нужны структурированные результаты и защита от конкурирующего сохранения.

Изучи core.py, app.py (main, entrypoint, privileged), tests/test_core.py, tests/test_profiles.py и scripts/install.sh (изолированный launcher). Архитектура — ARCHITECTURE.md. Проверить git status и записать фактический HEAD перед началом; этот TASK будет отдельным подготовительным commit Codex.

## Цель

GUI и Textual получают общий независимый от UI клиент: чтение состояния, вызов фиксированных административных операций, результаты busy/conflict/auth/error. Устаревшая операция с файлами отклоняется под общей блокировкой до записи. Самих GUI/Textual в этом TASK нет.

## Архитектурные решения Codex

- Без постоянного daemon, HTTP или D-Bus-сервера. Клиент запускает установленный `/usr/local/bin/zapret-console` отдельным процессом. Не выполнять исходники из пользовательской папки с root.
- Новый скрытый CLI-режим `--request-json <JSON>` — внутренний протокол. Его нельзя совмещать с другими режимами. Старые --admin, --status/--json и прочие команды сохраняются.
- Протокол v1: запрос `{ "protocol": 1, "action": "...", "value": null, "expected_revision": "..." }`. Разрешены только существующие административные действия; value — строка или null. Не принимать пути, имя сервиса, произвольные команды или другой контекст от клиента.
- Ответ — ровно один JSON-объект в stdout: `{ "protocol": 1, "ok": true|false, "code": "...", "message": "...", "data": ... }`. Коды: ok, busy, conflict, invalid_request, permission_denied, operation_failed. Exit code 0 для ok, 1 для остальных. Сообщение — для пользователя, логика клиента использует code.
- Клиент добавляет собственные transport_error, auth_cancelled и auth_failed для случая, когда helper не дал корректного ответа. Не угадывать успешность по тексту stderr.

## Что сделать

1. Общий snapshot в core: текущая конфигурация, состояние сервиса/автозапуска, профили и непрозрачная revision. Чтение не запрашивает root и не изменяет файлы. GUI/TUI смогут обновлять snapshot после операции или conflict.
2. Revision — SHA-256 детерминированного представления идентичности backend (root/unit), исходных байтов conf.env, known-good.json, previous.json и всех допустимых именованных `<name>.json`. Отсутствие файла/каталога явно отражается; содержимое .lock, временные файлы, mtime, диагностические отчёты и изменчивое состояние systemd в revision не входят. Имена сортировать. Данные профиля/конфигурации и соответствующие байты для revision получать из одного чтения каждого файла, без повторного чтения для отображения. Не открывать ссылки вместо каталога или именованного профиля.
3. Повреждённый именованный JSON учитывается в revision как байты, а в данных помечается недоступным, не ломая весь snapshot. Ошибка конфигурации или чтения отражается явно; не выдавать неполный snapshot за пригодный для сохранения.
4. Новый запрос для strategy/interface/save-good/restore-good/restore-previous и всех profile-* требует корректный expected_revision. В общем административном пути после получения root, общей блокировки и проверок доверенности заново вычислить revision и сравнить до любых записей профилей, previous.json, conf.env или вызова restart. При несовпадении — conflict и сообщение о необходимости обновить данные. Под блокировкой выполняются проверка и действие; нельзя отпускать её между ними или получать flock второй раз внутри dispatch.
5. Операции start/stop/restart/enable/disable остаются явными, без относительного toggle, и используют общую блокировку. runtime read-only остаётся без lock и без требования revision. Старый --admin сохраняет прежний контракт и поведение для совместимости; новые интерфейсы используют защищённый новый протокол.
6. Выделить BusyError/ConflictError как подклассы RuntimeError, чтобы старые обработчики продолжали работать. Машинный endpoint обрабатывает ошибки включая чтение settings и валидацию JSON без traceback или человеческого вывода в stdout. Некорректный запрос отклоняется до dispatch; ограничить размер запроса 64 KiB и строго проверять схему, action и типы. protocol=True не равен корректной целочисленной версии. Ошибки argparse для остальных режимов не менять.
7. Создать client.py с операциями чтения snapshot и выполнения запроса. Возвращать структурированные данные; не использовать print/input/clear/whiptail и не импортировать Qt/Textual. Не выполнять автоматический повтор мутации при busy, conflict, timeout или неясном результате.
8. Режим terminal: `sudo -- <fixed-launcher> --request-json <JSON>` со списком аргументов, без shell. stdin/stderr наследуются от терминала для пароля, stdout захватывается для JSON. Наличие TTY явно проверяется; при отсутствии не пытаться интерактивно запрашивать пароль. Будущий Textual приостанавливает экран на время авторизации — сам UI здесь не реализуется.
9. Режим gui: `pkexec --disable-internal-agent <fixed-launcher> --request-json <JSON>`, stdin DEVNULL; stdout/stderr захватываются. Авторизация через агент desktop-сессии, без текстового fallback и без запуска окна с root. Отмена pkexec (126 без корректного ответа helper) => auth_cancelled; отказ/ошибка авторизации (127) => auth_failed. Если root уже есть, вызвать фиксированный launcher без повышения прав. Не собирать и не хранить пароль.
10. Перед вызовом проверять наличие и доверенность установленного launcher; отсутствие утилиты — явный результат, без fallback на root-запуск python из репозитория. Разобрать ответ и проверить protocol, ok/code и структуру. Невалидный stdout, несовместимая установленная версия, ошибка запуска или timeout => transport_error. Timeout не доказывает отмену изменений: сообщать, что результат неизвестен и нужно перечитать состояние; не повторять запрос автоматически.
11. Покрыть unittest: snapshot/revision, конфликт двух клиентов, удержание общей блокировки, endpoint и транспорт. Отдельно проверить отсутствие DISPLAY для terminal-режима: оно не должно влиять на CLI и sudo-путь.

## Scope

Входит: core, новый client.py, машинный endpoint app.py и релевантные тесты. При необходимости кратко описать внутренний протокол в docstring нового модуля.

Не входит: QML/Qt, Textual, новые зависимости, миграция whiptail на новый клиент, изменение системных политик polkit, установка, redesign диагностики. PRODUCT.md, ARCHITECTURE.md, TASKS.md, DECISIONS.md и TASK-файл не менять.

## Ожидаемое поведение

Два клиента читают revision R. Первый сохраняет профиль — файлы меняются, появляется новая revision. Второй отправляет запрос со старой R и получает conflict; файлы и сервис этим запросом не меняются. После нового snapshot пользователь может повторно подтвердить действие. Если другой процесс удерживает lock — busy без изменения файлов. Отмена авторизации не выполняет helper.

Проверка revision сравнивает текущее содержимое, а не историю всех промежуточных состояний: изменение с возвратом абсолютно тех же байтов допустимо считать тем же состоянием. Это не журнал событий и не гарантия отсутствия ручных изменений root в обход нашего lock.

## Критерии приёмки

1. Все 69 принятых тестов сохраняют поведенческие утверждения и проходят; старые CLI-контракты не изменены.
2. Snapshot не меняет файлов, revision воспроизводима, изменяется при изменении/создании/удалении профилей, конфигурации и старых профилей. Отсутствие profiles нормально.
3. Устаревшая мутация даёт conflict до записи любого файла и до restart; два конкурирующих запроса не проходят одной устаревшей revision после изменения файлов первым.
4. Отказ busy структурирован; общий lock покрывает проверку revision, действие, restart и rollback.
5. Восстановление и повторная запись используют существующие validate/apply_config/защиты путей, без обходных реализаций.
6. Запрос не позволяет клиенту выбирать исполняемый код, пути или сервис. Некорректные типы, неизвестные поля/action/protocol, отсутствие revision для файловых действий отклоняются без dispatch.
7. Ответы endpoint — чистый JSON при штатных ошибках; клиент отличает busy, conflict, отмену и отсутствие авторизации от transport_error.
8. С помощью mocks проверены точные argv/stdin/stdout/stderr для sudo/pkexec, отмена, неверный JSON и timeout; автоматического повтора нет. Никакая проверка не меняет настоящий сервис и не запускает реальный парольный диалог.
9. CLI и terminal-клиент не требуют DISPLAY; import client не запускает subprocess и не требует Qt/Textual.
